# 外部基准核查（2026-09-24）

目的：论文最大的弱点是**任务全部由本项目作者设计**。这份文件记录对外部、非自建基准的核查结果，以及能否接到 HESP 的判断。

结论先写：**ExCyTIn-Bench 是目前唯一值得投入的候选，但它不能原样运行 HESP，必须做一层有代价的适配。**

## ExCyTIn-Bench 事实核查

- 论文 [arXiv:2507.14201](https://arxiv.org/abs/2507.14201)，ICML 2026 录用；仓库 [microsoft/SecRL](https://github.com/microsoft/SecRL)（MIT，154 star，2026-08 仍在更新）。
- **8 个事件**（模拟真实攻击链，如 Manatee Tempest 勒索、BEC 账号接管），每事件 7–7739 条告警、约 45 张表、11.5 万–36.5 万行。
- 问题由**调查图**（二部图：告警节点 ↔ 实体节点 IoC）上的最短路径成对生成；起点作背景、终点实体作答案。最新 `opus5` 题集共 1017 题（599 test / 418 train），按事件分成 8 个 JSON。
- 数据来自 "Alpine Ski House" —— 一个**配置完整但虚构的 Azure 租户**，用真实 Sentinel 工具链采集模拟的公司活动与攻击。**不是生产环境遥测**。
- 环境：`data_anonymized.tar.gz`（单事件库合计 10GB，全量 33GB）+ **MySQL 9 / 8 个 Docker 容器**，不需要 Azure；Python 3.11。
- 评分：先字符串匹配或 GPT-4o 判分，答对记 1.0；答错则按 `solution` 的中间步骤倒序给衰减分（γ=0.4）。人工复核 163 条与判分器 100% 一致。
- 参考成本：GPT-4o 跑完 589 题约 $0.24，平均约 11 步。

题目 JSON 的字段：`context / question / answer / solution / start_alert / end_alert / start_entities / end_entities / shortest_alert_path`。

## 与 HESP 的接口差距

| HESP 需要 | ExCyTIn 提供 | |
| --- | --- | --- |
| 有限假设集合 H | 开放式实体答案，**不给候选集** | 缺口 |
| 有限、带成本的探针目录 A | 自由 SQL，动作空间无界 | 缺口 |
| 预测模型 P(o\|h,a) | 无 | 缺口 |
| 确定性验证器（signature） | GPT-4o 判分 + 字符串匹配 | 需替换 |

**因此 ExCyTIn-Bench 不能直接跑 HESP。** 它测的是"会不会写 SQL 逐步挖"，HESP 测的是"在有限动作里怎么选最有区分力的一步"。

## 可行的适配方案（代价与风险）

把**数据和真值留给 Microsoft，只由本项目提供动作抽象**：

1. **H**：用他们发布的调查图，取同一事件内与答案**同类型**的实体节点作候选集。候选集由外部图机械导出，不是我们编的。
2. **A**：在约 45 张表上定义一组**参数化 SQL 模板**（如 `signins_for_account(x)`、`network_events_for_ip(x)`、`processes_on_device(x)`），每个带成本。这一层是我们设计的，必须明写。
3. **P(o\|h,a)**：**只从 418 条 train 题估计**，test 事件的任何内容都不得进入。—— 这正好是当前最高优先级的"非 oracle 预测"实验。
4. **验证器**：实体值归一化后精确匹配，不用 GPT-4o 判分（省掉 API key 与费用，也保持确定性）。代价是分数与官方榜单**不可比**。

### 必须如实披露的风险

- **只有 8 个事件。** 为防泄漏必须按事件聚类留出，那么测试端只有 3–4 个聚类，任务级 bootstrap 区间几乎没有分辨力。**这是这条路线最大的统计威胁**，应改用留一事件交叉验证并直接报告每个事件的结果，而不是硬套区间。
- **数据是模拟租户，不是生产遥测。** 只能说"外部团队发布的受控安全调查基准"，不能说"真实 SOC 数据"。
- **探针目录仍由我们设计。** 从"任务和动作都是我们出的"变成"任务和数据是外部的、动作抽象是我们的"，是实质改善但不是彻底解决。
- **改了动作空间就与官方榜单不可比**，应同时在相同事件上跑一组自由 SQL 基线做参照，并把方案写成"HESP on ExCyTIn data"而非"HESP on ExCyTIn-Bench"。
- 基础设施：10–33GB 数据 + 8 个 MySQL 容器（本机 Docker 28.3.2、E: 剩余 171GB，可行；纯 CPU，不需要 GPU 实例）。

## 建议

先做**只读可行性验证**，不承诺完整实验：拉取单个事件的库（约 1–2GB），跑通"题目 → 候选集导出 → 模板探针 → 实体匹配"的闭环，确认候选集能机械导出、模板覆盖率够用。这一步失败就放弃这条路线，不要先下载 33GB。
