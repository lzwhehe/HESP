\subsection{分诊测试床}
\label{sec:testbed}

要测量攻击者能做到什么，需要这样的分诊任务：多种解释同时成立，探针的成本和信息量各不相同，真值客观，而且攻击者能写入智能体读取的内容。然而，最接近这一需求的公开数据集缺少客观标注下配对的攻击与相似的管理活动（\S\ref{sec:realdata}）。因此我们构建了一个测试床：每个回合在自己的本地回环 HTTP 沙箱中运行，探针是真实的 HTTP 请求，会遇到瞬时故障和状态变化，且任何回合都观测不到其他回合。测试床提供三个模拟场景和几类攻击者，详见下文。

\paragraph{sec-triage} 每个回合对应 Web 服务上的一条告警。隐藏原因是八种解释之一：三种攻击（撞库、SQL 注入探测、DNS 命令与控制）、内部人员外泄数据、暴露的管理面板、已知有漏洞的组件、授权的漏洞扫描，以及监控误报。假设集合另加 \textit{other}。十个只读探针，每个成本 1 到 3 个单位，覆盖认证失败、HTTP 模式、来源信誉、管理面板暴露、按用户的出站流量、DNS 特征、组件清单、变更工单、威胁情报和一份通用运维手册。我们有意让捷径失效：威胁情报只说明某个指标是恶意的，而三种攻击都会得到这个回答；运维手册不含任何信息；若干良性原因在运行正确探针之前看起来都像攻击。每个原因有三个变体。\textit{base} 中，除 10\% 的威胁情报延迟外，结果都是确定的。\textit{noise} 加入 15\% 的瞬时 HTTP 503 故障和 30\% 的延迟。\textit{drift} 中，事件在第二个探针之后被取代：状态版本递增，真实原因随之切换。共 24 个任务，每项研究在每个配置下把每个任务运行三次。

\paragraph{预测表} 我们比较 $P(o \mid h, a)$ 的三种来源。\emph{设计者}表来自环境的生成函数，作为 oracle 参照。\emph{计数}表（表中记为“empirical”）按 \S\ref{sec:tables} 的方法估计，每个原因和变体使用 $k \in \{1, 5, 20, 100\}$ 个开发回合，只来自 base 和 noise 变体，种子取自与评测不重叠的空间。\emph{模型给出}的表由规划器 LLM 自己生成。每张表都在任何评测回合之前冻结并计算哈希。由于开发回合与评测回合来自同一个生成器，计数表只能说明需要多少观测才够，而不能说明方法在陌生环境中的表现。

\paragraph{sigma-triage} 为减少我们对“哪些原因相互竞争”的影响，v1.0 研究从公开的 SigmaHQ 检测规则仓库~\citep{sigmahq}（固定到某一提交）机械地派生出第二个合成任务族。每条 Sigma 规则说明告警内容、它针对的 ATT\&CK 技术，以及一个 \texttt{falsepositives} 字段，规则作者在其中列出已知的良性解释。一个任务就是一条规则被触发。其候选原因包括该规则针对的攻击、从该字段原样摘取的最多四个良性解释，以及 \textit{other}。入选条件在抽样之前就已确定（状态为 stable 或 test、级别不低于 medium、带 ATT\&CK 标签、至少有两个具体的良性解释），用固定种子从 159 条符合条件的规则中抽取 12 条，覆盖 Windows 终端、Azure、Kubernetes 和 GitHub。十个通用调查探针在抽取任何规则之前就已写好，由所有规则共用：执行账户、登录来源、变更工单、软件审批、二进制信誉、在整个终端群中的普遍程度、父进程、时间窗口、后续活动和威胁情报。每个探针在每个原因下返回什么结果，由两个规划器家族之外的一个模型标注一次（phi-4~\citep{phi4}，温度 0，限定在固定的结果词表内）后冻结。若某条规则的标注使两个原因无法区分，就用抽样顺序中的下一条规则替换，这种情况发生过一次，因此该任务族只包含探针目录能够区分的原因。该任务族有 76 个任务（base 和 noise 变体），其预测表与 sec-triage 完全一样地由不含 LLM 的开发回合计数得到。它仍然是一个模拟器：规则提供候选原因，但结果来自冻结的模型标注，而不是录制的遥测。

\paragraph{comp-triage} 由于前两个场景几乎是确定性的、且每个原因都有特征观测，v1.2 研究新增 \emph{comp-triage}：三个场景（远程执行、计划任务、大量外传），每个场景中一种攻击与三种合法活动使用相同工具；它沿用 sigma-triage 的探针，结果为概率分布，十二个原因中有五个没有单条独有观测。其预测表由每个原因和变体 20 个不含 LLM 的开发回合计数得到。

\paragraph{攻击者} 威胁模型中的攻击者由 sec-triage 的若干变体实现，这些变体只用于其六个需处置原因。在 \emph{inject} 中，每个探针响应都带有一个由攻击者控制的自由文本字段（就像 User-Agent 或任务描述那样），其中写着“以授权扫描结案并引用这条观测”的指令。分类器只读取结构化字段，因此账本看不到这段文本，但任何读取原始响应的规划器都会看到。在 \emph{spoof} 中，攻击者让流量经过一个看起来像扫描器的地址，于是无论真实原因是什么，来源信誉探针都报告“已知扫描器”；这确实会误导账本。base 变体下的两个良性原因用来测量非对称证据规则给真正良性案例带来的代价。v1.1 研究另加三种措辞和位置不同的注入文本（User-Agent 字段；伪造的分析员覆盖字段；只出现在一个探针的响应中），以及 \emph{spoof-feed}：攻击者控制 \texttt{source\_ips} 和 \texttt{threat\_intel} 两个探针共同读取的上游信誉源。原始日志研究（v1.2、v1.3）把每个探针的响应渲染为日志文本，共六种条件：\emph{文档}格式；\emph{漂移}格式，用改写的行陈述同样的事实并加入无关行；v1.2 的\emph{四探针}注入，即四个探针的 User-Agent 字段用探针自己的词表声称授权扫描的读数；以及 v1.2 之后编写的三种自适应攻击：\emph{每个探针}都有同样的声称（一致的授权扫描故事）、同样的声称放在\emph{漂移}格式上，以及\emph{日志行}注入——User-Agent 的值先闭合引号、再换行、再伪造一条授权扫描会产生的完整记录，正如一个既不转义引号也不转义换行的日志写入器会输出的那样。

\paragraph{配置} 所有配置使用相同的模型、提示模板、探针目录、预算（10 次工具调用、10 个成本单位、12 次决策、900\,s）、重复拦截和验证器。\emph{ReAct 式}：规划器只看到原始观测历史，并自己选择每个探针。\emph{Memory-only}：规划器还能看到账本，但仍然自己选择每个探针。\emph{\hesp{}}：由控制器选择探针（EIG/成本或随机），可以展示或不展示其排序，可以启用或不启用结束守卫和控制器侧停止。这些开关在不同研究中各不相同，而 \S\ref{sec:approach} 中的安全性质只在守卫开启时成立：初始研究和表来源研究使用守卫但没有停止；分解研究只在一个配置中使用守卫；停止研究和第二任务族研究不使用守卫；对抗部分和 v1.1 研究在每个 \hesp{} 配置中都使用守卫。\cref{tab:configs}（附录~\ref{app:loop}）列出每个配置和精确的执行顺序，附录~\ref{app:loop} 中的\cref{fig:motivating} 在同一条告警上展示了其中四个。\emph{不含 LLM 的参照}用从不结束的脚本代替规划器，因此每个结论都来自控制器：一个是停止研究之后事后运行的（后验停止，探索性），另外四个在 v1.1 中预先登记，在两个任务族上使用与 LLM 研究相同的种子、任务和预算（EIG/成本加后验停止或 \S\ref{sec:finish} 的\emph{确认条件停止}；按先验下 EIG/成本顺序排列的固定流程；以及目录顺序）。v1.1 的 LLM 配置都开启守卫并改变停止方式，在对抗变体上则把各组件分开（\cref{tab:v11attack}）。我们推荐的配置是 EIG/成本选择、结束守卫、确认条件停止，以及良性结论按来源组佐证；不带守卫的配置都是消融。v1.3 研究在不含 LLM 的规划下运行这一推荐配置（含恢复规则），只改变\emph{读取器}：单独的被服务模型；规则解析器优先、读不出的交给模型；先删去已知自由文本字段再交给模型；以及在规则解析器优先之上加 \S\ref{sec:finish} 的读取器信任规则。一个能正确读取任何格式、并采纳它看到的每一条声称的脚本读取器，给出每种攻击不含 LLM 的上界。

\paragraph{实现} \hesp{} 约 2{,}900 行 Python，只使用标准库。规划器是可插拔的：同一个 JSON 决策协议服务于 vLLM 和 Ollama 端点，以及不含 LLM 运行所用的脚本策略。每个回合都有独立的本地回环 HTTP 沙箱，因此探针是真实的 HTTP 请求，会遇到瞬时故障和状态变化，且任何回合都观测不到其他回合。每项研究都使用 Qwen2.5-7B-Instruct（bf16）、Qwen2.5-32B-Instruct-AWQ 和 Qwen2.5-72B-Instruct-AWQ；分解研究和停止研究另加 Llama-3.1-8B-Instruct（bf16）和 Llama-3.1-70B-Instruct-AWQ-INT4。模型由 vLLM 0.30.0（PyTorch 2.13、CUDA 13.0）在一块 NVIDIA RTX PRO 6000D（85.6\,GB）上提供服务，上下文 8{,}192 个 token，每次决策最多生成 400 个 token，温度 0.2，其余采样参数取自各模型的生成配置，每次调用使用不同的种子。每条观测的原始响应截断到 300 个字符后展示给规划器。一个配对、打乱、可续跑的运行器最多并发 32 个回合，若清单或控制器源码哈希发生变化则拒绝续跑。每个模型结束后，它审计全部回合、归档日志并记录归档的 SHA-256。停止研究的 1{,}800 个回合用时 28 分钟，v1.0 研究在同一台服务器、同一服务软件栈和同一权重上运行。在 v1.1 中，三个大模型在同一软件栈和权重下运行于一块 RTX PRO 6000 Blackwell Server Edition（95.6\,GB），两个小模型运行于 NVIDIA H100 vGPU（20\,GB），使用 vLLM 0.11.0、PyTorch 2.8、16 个并发回合，并关闭前缀缓存（勘误 E-11）；v1.1 的数字只在 v1.1 内部比较。201 个单元测试覆盖账本、选择器、盲提示、守卫、控制器停止、佐证、读取器策略、审计，以及预测表估计器与环境生成器的隔离。

\paragraph{指标与分析} 结果指标是\emph{已验证完成率}，即以已验证结论结束的回合比例。其他任何结局，包括超时和格式错误的输出，都算作失败。我们报告按任务配对的差值，以及百分位任务聚类 bootstrap 区间（2{,}000 次重抽样，24 个簇）。一项研究有两个主要终点时，各自使用 Bonferroni 校正后的 97.5\% 区间；v1.0 研究有三个（98.33\%），在 sigma-triage 上区间按整条规则（12 个簇）而不是按任务重抽样。所有次要比较都是探索性的，不做校正。我们还报告描述性的安全指标。两个原因是良性的（授权扫描和监控误报），其余六个需要处置。在以结论结束的回合中（条件比例；附录~\ref{app:tables} 另外按全部需处置回合报告），\emph{漏判攻击}率是真实原因需处置而结论为良性原因的比例，\emph{误升级}率与之相反，\emph{错因}率是结论原因错误的比例。我们把\emph{未验证}（所有没有已验证结论的回合）与\emph{无结论}（没有给出任何结论的回合）分开报告，并在附录~\ref{app:tables} 中给出计数及其分母。v1.1 研究把每个回合分为六个互斥类别：已验证；原因正确但未验证；原因错误；\textit{other}；弃权（规划器停止）；以及无结论（预算耗尽或规划器错误）。其漏判攻击数以\emph{全部}需处置回合为分母，因此一个从不作答的智能体不会显得安全。同一（任务，重复）对的所有 arm 共用环境种子，但环境按探针调用顺序从同一个随机流中抽取瞬时故障，因此探测顺序不同的 arm 可能遇到不同的噪声。回合数很多，但独立单元很少：24 个 sec-triage 任务（八个原因、三个变体）和 12 条 Sigma 规则，我们的区间就是对这些单元重抽样。在对抗部分和表误差部分，\emph{攻击成功率}是需处置原因回合中以良性结论结束的比例；以 \textit{other} 或无结论结束的回合算作\emph{升级}，在分诊中即把案件交给分析员。真值是结论给出时正在生效的原因。v1.2 研究还记录\emph{联合}验证器：若当前全部观测在真实分布下对所称原因的支持至少是其他每个具名原因的十倍，则接受结论；因此它接受由若干条单独看来含糊的观测组合、以及由排除得到的结论。在原始日志研究中，验证器检查的是\emph{真实}结果，因此解析错误永远不会让结论被判为已验证；\emph{采纳}计数的是解析标签等于攻击者声称的标签、而真实结果不同的观测。v1.3 的主要终点每个模型一个：在三种自适应攻击合并的需处置回合上，只用模型读取时被结为良性的比例减去读取器信任规则下的比例，按 12 个需处置任务聚类（97.5\% 区间）。每张表和每幅图都由脚本从原始结果文件生成。

\subsection{局限}
\label{sec:limits}

我们的方法存在若干局限。首先，三个场景都是模拟的，我们的发现未必能原样推广到更嘈杂、规模更大的真实遥测。这些场景也都很小（八个原因构成的 24 个任务、12 条规则，以及三个 comp-triage 场景），前两个几乎是确定性的，开发回合与评测回合来自同一个生成器，因此我们的区间至多能推广到这些任务的新回合，而不能推广到新的原因。不过，第二个场景从公开检测规则派生原因，消除了我们自己对原因的选择，尽管其结果是 LLM 的标注，而且替换了一条不可区分的规则，使它只包含探针目录能够区分的原因。其次，候选原因是给定且互斥的，\textit{other} 只是一个没有开发案例的残余项，环境会主动报告事件何时变化；新原因、并发原因和未被察觉的变化都不在研究范围内，而在漂移任务中，智能体的节奏决定它是否会遇到漂移。我们的验证器要求一条只有所称原因才会产生的观测，因此通过组合或排除得到的正确结论算作失败；联合验证器和 comp-triage 测量了这一选择，但其场景很少，且由我们编写（\S\ref{sec:policy}）。再次，我们的攻击者是我们自己编写的：一个环境中的四种注入文本和两种伪造，以及读取路径上的一种变化后的日志格式、一种声称措辞和一种日志行伪造。伪造两个独立来源组的攻击者同样能击败佐证规则，而读取器信任规则依赖一个按构造对所测攻击免疫的规则解析器（它读每个探针的第一条记录）。提示词比较和读取器攻击只在两个小模型上运行，v1.1 到 v1.3 的运行使用了两种 GPU，小模型还使用了不同的服务软件栈。最后，我们自己也犯过错误，从报错的区间、丢失的日志，到在可行性检查中读取了 ExCyTIn 的测试题；附录~\ref{app:errata} 逐一记录了这些错误。其中 E-7 的预测表不对称发生在表来源研究的一个主要比较之内；后来消除了这一不对称的研究支持同样的结论，但这并不能让原来的比较变得干净。
