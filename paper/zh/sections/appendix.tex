\section{执行循环与配置}
\label{app:loop}

\paragraph{执行顺序} 一个回合重复执行以下循环直到结束；步骤编号对应仓库中的 \texttt{controller.run}。
\begin{enumerate}\setlength\itemsep{0pt}
  \item 若时间预算用完，结束（无结论）。
  \item 若环境的状态版本发生变化，把当前分数重置为先验，早先证据保留为历史。
  \item \emph{控制器停止}（若启用）：若领先原因后验 $\ge 0.8$ 且有当前观测支持它（在确认条件下须\emph{特异地}支持），并满足可能的良性佐证要求，则引用最多三条支持观测给出结论，不再调用规划器。
  \item 按 EIG/成本对合法探针（当前状态下未运行、在预算内、前置条件满足）排序。
  \item 向规划器发送一个请求（账本、历史、被拦截提议、剩余预算；仅在展示时附上排序），得到一个决策。格式错误的回复连同错误返回一次；再次出错则结束回合（\emph{规划器错误}）。
  \item \texttt{stop}：无结论结束（\emph{弃权}）。
  \item \texttt{finish}：若启用结束守卫且结论不满足（分数 $< 0.8$、未引用支持它的当前观测，或缺少良性佐证），则拒绝，把原因加入被拦截提议，回到第 1 步；这次拒绝消耗一次决策。否则以规划器的结论结束。
  \item \texttt{action}：在 Memory-only 和 ReAct 式配置中运行所提议的探针；在 \hesp{} 配置中，无论提议了什么，都由控制器的选择器选定探针。同一状态下的重复探针会被拦截，并消耗一次决策。
  \item 把每个原因下的预测 $P(o \mid h, a)$ 写入日志，执行探针，记录观测，更新账本。瞬时故障会被记录、可以重试，但不作为证据。
\end{enumerate}
当决策预算、工具预算或合法探针耗尽时，控制器停止（若启用）再执行一次。验证器对每个结论调用一次，只用于记录评测结果；其结果从不传给控制器或规划器。因此，在启用控制器停止且其接受规则与守卫相同的配置中，规则一旦满足，规划器就不会再被询问；强模型“等待确认”的价值（\S\ref{sec:rq-stop}）是在\emph{不启用}控制器停止的配置中测得的。

\section{公开数据审查}
\label{app:public}

要检验控制器是否善于选择探针，需要三个条件。(i) 仅凭告警不能得出答案，必须有多种解释同时成立。(ii) 探针的成本和信息量必须不同，使顺序有意义。(iii) 真值必须客观，反映实际发生了什么，而不是一种标注惯例。附录~\ref{app:licences} 列出了读取的版本和文件。

\paragraph{ExCyTIn-Bench~\citep{excytin}} ExCyTIn 针对一个模拟 Azure 租户的日志提出问题，智能体用 SQL 查询。答案可以从公开的调查图中机械还原（\texttt{opus5} 题集 1{,}017 题中的 98.5\%）；调查图是评测方的答案来源，智能体看不到，因此这说明的是题目如何生成，而不是智能体有捷径。在 418 道训练题中，54.8\% 在题面中直接点名目标告警，其余大多是换一种说法，所以任务是定位被点名的告警并读出一个实体。标准的指标关联探针找到正确答案的频率并不高于干扰项（告警表中 0.571 对 0.570），只有 19.4\% 的题目存在能唯一定位答案的表。就我们考察的题目和我们适配的探针而言，这项任务更像导航和检索，而不是在相互竞争的解释之间做选择；该基准的其他适配方式可能更合适。

\paragraph{GUIDE~\citep{guide}} GUIDE 包含来自 5{,}340 个组织的 707{,}108 起真实的匿名事件，分级为真阳性、良性阳性或假阳性。在其告警元数据上的十个事件级探针中，仅组织身份就携带了分级 1.50 比特熵中的 1.03 比特，几个大型组织对所有事件都给同一个分级。在组织内部，查询该组织以前如何给同一检测器分级即可达到 0.911 的准确率；跨组织时，这些探针都不优于多数类。在冷启动事件上（训练数据内按组织做时间切分：组织—检测器组合历史很少或混杂的最新 20\% 事件），证据整合对真阳性与其余两级的排序 AUROC 为 0.755，与历史查表（0.759）相同（差 $-0.004$ $[-0.028,+0.027]$，按组织重抽样）。分级强烈依赖于组织，这可能反映策略、基率或检测器构成；我们没有把这些因素分开，并暂停了原计划的 GUIDE 研究。其测试集至今未读取。

\paragraph{OTRF Security-Datasets~\citep{otrf}} OTRF 包含执行 ATT\&CK 技术时采集的 Windows 主机遥测实验室录制，没有良性活动录制。我们审查了远程执行类的 27 份录制（243{,}000 个事件），把每次服务安装和计划任务创建或更新视为告警，并依据录制的元数据标注。46 条不同告警中，8 条是攻击，38 条是操作系统的后台事件。一条只看告警文本的规则——判断任务或服务是否属于 Windows 组件——在 46 条中判对 44 条，因为 8 次攻击中有 6 次以其工具命名。这一结论只适用于我们审查的 27 份录制和两类事件，而不是整个 OTRF。

\paragraph{案例研究} 在这些录制中，唯一确实需要调查的 OTRF 场景是一个伪装成 Windows 维护任务的计划任务；尽管它的告警文本看起来是良性的，两个低成本探针就能把它与其他任务事件区分开，详见附录~\ref{app:case}。在这个样本中，一个探针（创建账户）就已足以区分；由于缺少合法远程管理的对照，该案例只作为定性证据。

\paragraph{共同的缺口} 在我们考察的子集中，缺少的东西是一样的：看起来像日常管理的攻击，以及看起来像攻击的日常管理。在我们审查的 OTRF 录制中，良性事件是操作系统的日常维护，而不是管理员合法地使用同样的工具，攻击模拟也留下了工具痕迹。要在真实遥测上评测分诊智能体，需要这种配对且客观标注的数据。

\section{案例研究：伪装成 Windows 任务的计划任务}
\label{app:case}

这个唯一确实需要调查的 OTRF 场景，在真实日志上展示了 \hesp{} 所针对的那类案例。其元数据引用了微软对 Solorigate 入侵的分析~\citep{solorigate}，并把该活动标为远程计划任务创建（T1053.005）。告警是 \texttt{WORKSTATION6} 上的安全事件 4698，报告在文件夹 \texttt{\textbackslash Microsoft\textbackslash Windows\textbackslash Software\-Protection\-Platform} 中新建了任务 \texttt{EventCacheManager}，文件夹和名称都与真实的 Windows 任务吻合；只看文本的规则判其为良性。第一个探针发现它由域用户 \texttt{THESHIRE\textbackslash pgustavo} 创建，而 27 份录制中 \texttt{\textbackslash Microsoft\textbackslash Windows} 下的其余 17 个任务事件全部由机器账户创建。第二个探针发现创建会话是来自另一台主机的网络登录（类型 3，Kerberos），从而排除了本地持久化和用户上下文的更新程序。该任务以 SYSTEM 身份运行 \texttt{cmd.exe}，源主机的进程日志显示了创建它的 \texttt{schtasks /create \dots{} /s} 命令。告警文本与调查结果指向相反方向，两个低成本探针就能把它们分开。由于一个探针就已足够且场景唯一，该案例不能说明探针顺序的重要性；我们只把它作为定性证据。

\section{设计取舍}
\label{app:alternatives}

每个设计选择都替换了一个我们实现并测量过的替代方案。在每个 \hesp{} 配置中，控制器都执行自己的选择；唯一的变化是是否同时向规划器展示排序，这对完成率的影响至多 $+0.06$（分解研究）。让规划器在看到排序的情况下自行选择，相当于 Memory-only 加排序，我们没有运行这一配置。一个考虑预算的两步前瞻选择器在我们开发它的任务族上比 EIG/成本高 $+0.17$ 到 $+0.21$，但在一个保留的任务族上（3{,}888 个回合）持平或落后于 EIG/成本，7B 规划器下落后 $-0.125$；在 sec-triage 上，三个 Qwen 模型分别完成 0.889、0.972 和 0.958，而 EIG/成本为 0.958、1.000 和 1.000；因此我们保留了贪心规则。在我们的提示下，向规划器展示超过 0.999 的后验并说明已无合法探针，并不能让 Llama-3.1-8B 给出结论，而由控制器执行的停止规则可以。不启用结束守卫时完成率变化至多 $+0.04$，但守卫保证每个被接受的结论都引用了当前的支持证据，因此我们保留它。

\section{勘误}
\label{app:errata}

\begin{description}
  \item[E-1] 初始研究曾报告三个主要区间都不含零；72B 的区间实际为 $[0.000, 0.236]$。
  \item[E-2] 初始研究的逐回合日志没有在租用的 GPU 释放之前归档。汇总结果可以重算，但原始事件无法由第三方重新审计。从表来源研究开始，日志都在释放算力之前归档并计算哈希。
  \item[E-3] 初始研究的运行清单带有来自另一任务族早期研究的过时元数据。
  \item[E-4] 在初始研究中，随机选择对照能看到 EIG 排序。分解研究的盲变体消除了这一问题。
  \item[E-5] 在表来源研究之前，预测表来自环境的生成器。计数表取代了它们。
  \item[E-6] 描述性安全指标的真值对漂移回合处理有误，先后更正了两次。现在每个汇总脚本都检查每个已验证结论是否等于所用真值。
  \item[E-7] 在表来源研究中，Memory-only 的账本使用设计者表，而 \hesp{} 使用计数表。我们预期这一不对称有利于基线，但没有检验；LLM 对账本分数的反应可能是非单调的。分解研究对每个 arm 都使用计数表，消除了这一不对称。
  \item[E-8] v1.0 的冻结记录称没有使用镜像权重。事实上，自分解研究起，两个 Llama-3.1 检查点都来自非门控镜像；它们与此前每项研究使用的是同一批文件。
  \item[E-9]（已披露的偏离。）v1.0 协议计划在另一块 20\,GB 的 GPU 上标注 Sigma 规则，但 phi-4 放不下。标注改在本研究自己的服务器上进行，模型、提示、模式和温度都相同，且在冻结任何内容之前完成；第一台机器没有产生任何标注。
  \item[E-10] \S\ref{sec:realdata} 和伦理部分曾称没有读取任何公开数据集的测试集。对 ExCyTIn-Bench 而言这是错误的：测量答案能否从调查图中还原（98.5\%）以及固定探针目录能否覆盖答案的两个可行性脚本，读取了 \texttt{opus5} 题集的全部 1{,}017 道题，包括 599 道测试题。只有后来的关联探针测量限于 418 道训练题。没有任何 ExCyTIn 结果用于评测 \hesp{}，也没有据此调整任何东西；该说法对 GUIDE 成立，其测试集至今未读取。
  \item[E-11]（v1.1，在分析之前披露。）v1.1 在 H100 服务器上第一次启动时，与 RTX PRO 6000D 上一样开启了前缀缓存。此时 vLLM 0.11 让同一服务上第二个研究的每个 JSON 模式请求都失败（xgrammar 报 “Failed to advance FSM”）；受控重跑在开启缓存时复现了这一问题，关闭缓存时没有复现。因此该服务器上所有 v1.1 GPU 运行都关闭前缀缓存，开启缓存时产生的两个研究目录未经分析即被丢弃。
\end{description}
