\section{Execution Loop and Configurations}
\label{app:loop}

\paragraph{Order of operations} One episode runs the following loop until it ends; the step numbers are those of \texttt{controller.run} in the repository.
\begin{enumerate}\setlength\itemsep{0pt}
  \item If the time budget is spent, end (no verdict).
  \item If the environment's state version changed, reset the current scores to the prior and keep earlier evidence as history.
  \item \emph{Controller stop} (if enabled): if the leader has posterior $\ge 0.8$ and a current observation supports it (under the confirmation rule, one that \emph{specifically} supports it), and any benign-corroboration requirement is met, conclude with up to three supporting observations. The planner is not called.
  \item Rank the legal probes (untried in this state, affordable, prerequisites met) by EIG/cost.
  \item Send the planner one request (ledger, history, blocked proposals, remaining budgets; the ranking only if shown) and receive one decision. A malformed reply is returned once with the error; a second one ends the episode (\emph{planner error}).
  \item \texttt{stop}: end without a verdict (\emph{abstained}).
  \item \texttt{finish}: if the finish guard is on and the claim fails it (score $< 0.8$, no cited current supporting observation, or missing benign corroboration), reject it, add the reason to the blocked proposals, and go to step~1; the rejection consumes a decision. Otherwise conclude with the planner's verdict.
  \item \texttt{action}: in Memory-only and ReAct-style configurations, the proposed probe runs; in \hesp{} configurations, the controller's selector chooses the probe, whatever was proposed. A duplicate in the same state is blocked and costs a decision.
  \item Journal the prediction $P(o \mid h, a)$ for every cause, execute the probe, journal the observation, and update the ledger. A transient failure is journaled and may be retried; it is not evidence.
\end{enumerate}
When the decision budget, tool budget, or legal probes run out, the controller stop (if enabled) is applied once more. The verifier is called on every verdict only to record the evaluation; its result never reaches the controller or the planner. Consequently, with the controller stop enabled and the same acceptance rule as the guard, the planner is never asked again once the rule is met; the value of a strong model ``waiting for confirmation'' (\S\ref{sec:rq-stop}) was measured in configurations \emph{without} the controller stop.

\paragraph{Disclosed pre-freeze runs} Before freezing the table-source, decomposition, and stopping studies, we ran pipeline smoke tests of 10 to 16 episodes. For the stopping study we also ran an LLM-free simulation on disjoint development seeds. None of these runs enters any analysis. The simulation informed the stated expectation for the controller-stop endpoint; the threshold of 0.8 was carried over from the finish guard and was not tuned. The LLM-free reference in \cref{tab:v09} was run after the stopping study and is exploratory. Before freezing the v1.0 study we ran pipeline smoke tests (8 adversarial and 20 sigma-triage episodes, and a reduced table-error run) and an LLM-free simulation of the adversarial variants on disjoint seeds. That simulation already showed that a forged scanner answer makes the controller close every actionable case as benign, and that the asymmetric-evidence rule prevents it; the protocol records this expectation before any LLM episode ran. The v1.0 source hash is unchanged from the adversarial and table-error parts to the second family: the family's code was written and tested before any rule was sampled. Before freezing v1.1 we ran smoke tests of every part; the first one failed on a serving fault that was later traced to prefix caching (E-11), and its episodes, like those of the two study directories discarded for the same reason, enter no analysis. Two further episode sets lie outside \cref{tab:studies}: the 3{,}888 episodes of Appendix~\ref{app:alternatives} come from an exploratory study (v0.4) on an earlier task family with its own protocol and seeds, and the 3{,}968 LLM-free episodes of v1.1-D are counted separately.

\section{Public Data Audit}
\label{app:public}

Testing whether a controller chooses probes well requires three things. (i) The alert alone must not reveal the answer, so several explanations must remain plausible. (ii) Probes must differ in cost and in how much they reveal, so that their order matters. (iii) Ground truth must be objective, reflecting what actually happened rather than a labeling convention. Appendix~\ref{app:licences} lists the versions and files read.

\paragraph{ExCyTIn-Bench~\citep{excytin}} ExCyTIn poses questions over a simulated Azure tenant's logs, which an agent queries in SQL. The answers can be recovered mechanically from the published investigation graphs (98.5\% of the 1{,}017 questions of the \texttt{opus5} set); the graphs are the evaluator's answer source and are not visible to an agent, so this shows how the questions were generated, not that an agent has a shortcut. On the 418 training questions, 54.8\% name the target alert in the question text, and most others paraphrase it, so the task is to locate the named alert and read an entity. The standard indicator-pivot probe finds the true answer no more often than distractors (0.571 against 0.570 in the alert table), and only 19.4\% of questions have any table that singles out the answer. The questions test navigation and retrieval, not investigation.

\paragraph{GUIDE~\citep{guide}} GUIDE contains 707{,}108 real, anonymized incidents from 5{,}340 organizations, graded as true positive, benign positive, or false positive. Over ten incident-level probes on its alert metadata, organization identity alone carries 1.03 of the grade's 1.50 bits of entropy, and several large organizations assign one grade to every incident. Within an organization, looking up how it previously graded the same detector reaches 0.911 accuracy, and across organizations the probes do not beat the majority class. On cold-start incidents (a within-organization time split of the training data: the latest 20\% of incidents whose organization--detector pair has little or mixed history), evidence integration ranks true positives against the other two grades with AUROC 0.755, equal to history lookup (0.759; difference $-0.004$ $[-0.028,+0.027]$, organizations resampled). The grade depends strongly on the organization, which may reflect policy, base rates, or detector mix; we did not separate these, and we paused the planned GUIDE study. Its test split remains unread.

\paragraph{OTRF Security-Datasets~\citep{otrf}} OTRF contains lab recordings of Windows host telemetry captured while ATT\&CK techniques were executed, with no benign-activity recordings. We audited 27 recordings from the remote-execution family (243{,}000 events), treated every service installation and scheduled-task creation or update as an alert, and labeled it from the recording's metadata. Of the 46 distinct alerts, 8 are attacks and 38 are background operating-system events. A one-glance rule on the alert text, which asks whether the task or service belongs to a Windows component, is correct on 44 of 46, because six of the eight attacks are named by their tooling. This holds for the 27 recordings and two event types we audited, not for OTRF as a whole.

\paragraph{Case study} The one OTRF scenario that does require investigation, a scheduled task masquerading as a Windows maintenance task, is separated from the other task events in these recordings by two cheap probes although its alert text looks benign; Appendix~\ref{app:case} gives the details. Within this sample one probe (the creating account) already separates it; without legitimate remote-administration counterparts, the case is qualitative evidence only.

\paragraph{The common gap} The three datasets fail in different ways, but the missing ingredient is the same: attacks that look like routine administration, and routine administration that looks like an attack. Their benign counterparts are operating-system housekeeping rather than administrators legitimately using the same tools, and their attack emulations leave artifacts that a careful adversary would not. Paired, objectively labeled data of this kind is a prerequisite for evaluating triage agents on real telemetry.

\section{Case Study: A Scheduled Task Masquerading as a Windows Task}
\label{app:case}

The one OTRF scenario that does require investigation shows, on real logs, the kind of case \hesp{} is built for. Its metadata references Microsoft's analysis of the Solorigate intrusion~\citep{solorigate} and labels the activity as remote scheduled-task creation (T1053.005). The alert, security event 4698 on \texttt{WORKSTATION6}, reports a new task \texttt{EventCacheManager} in the folder \texttt{\textbackslash Microsoft\textbackslash Windows\textbackslash Software\-Protection\-Platform}, whose folder and name match genuine Windows tasks; the text-only rule calls it benign. A first probe finds that the domain user \texttt{THESHIRE\textbackslash pgustavo} created it, whereas the other 17 task events under \texttt{\textbackslash Microsoft\textbackslash Windows} in the 27 recordings were all made by machine accounts. A second finds that the creating session is a network logon (type 3, Kerberos) from another host, which rules out local persistence and user-context updaters. The task runs \texttt{cmd.exe} as SYSTEM, and the source host's process log shows the \texttt{schtasks /create \dots{} /s} command that created it. The alert text and the investigation point in opposite directions, and two cheap probes separate them. Because one probe suffices and the scenario is unique, the case cannot show that probe order matters; we include it as qualitative evidence only.

\section{Design Alternatives}
\label{app:alternatives}

Each design choice replaced an alternative that we implemented and measured. In every \hesp{} configuration the controller executes its own choice; the only variation is whether the planner is also shown the ranking, which changes completion by at most $+0.06$ (decomposition study). Letting the planner choose with the ranking in view is Memory-only plus the ranking, which we did not run. A budget-aware two-step lookahead selector beat EIG/cost by $+0.17$ to $+0.21$ on the task family we developed it on, but on a held-out family (3{,}888 episodes) it matched or trailed EIG/cost, by $-0.125$ for the 7B planner, and on sec-triage it completed 0.889, 0.972, and 0.958 against 0.958, 1.000, and 1.000 for the three Qwen models; we kept the greedy rule. Showing the planner a posterior above 0.999 and stating that no legal probe is left does not make Llama-3.1-8B conclude, whereas a stopping rule enforced by the controller does. Without the finish guard, completion changes by at most $+0.04$, but the guard ensures that every accepted verdict cites current supporting evidence, so we keep it.

\section{Runtime and Cost}
\label{app:runtime}

End-to-end latency is dominated by LLM inference; ledger updates and selection take negligible time next to a model call. \Cref{tab:runtime} gives per-episode wall time, planner calls, and tokens in the stopping study. These were measured with 32 episodes sharing one GPU, so they include queueing and overstate the latency of a single investigation; the batch figure (1{,}800 episodes over five models in 28 minutes) is throughput, not latency. The controller stop cuts planner calls from 5.5--10.1 to 2.3 per episode and tokens by a factor of 2.5 to 5, and controller selection halves probe cost (for Llama-3.1-8B, from 4.78 to 2.35 units).

\section{Errata}
\label{app:errata}

\begin{description}
  \item[E-1] The initial study reported that all three primary intervals excluded zero; the 72B interval is $[0.000, 0.236]$.
  \item[E-2] The initial study's per-episode journals were not archived before the rented GPU was released. Summaries can be recomputed, but the raw events cannot be re-audited by third parties. From the table-source study on, journals are archived and hashed before compute is released.
  \item[E-3] The initial study's manifests carried stale metadata from an earlier study on another task family.
  \item[E-4] In the initial study, the random-selection control could see the EIG ranking. The blind variants of the decomposition study remove this.
  \item[E-5] Before the table-source study, prediction tables were derived from the environment's generator. The counted tables replace them.
  \item[E-6] The ground truth of the descriptive security metrics mishandled drifting episodes and was corrected twice. Every summary script now checks that each verified verdict equals the ground truth used.
  \item[E-7] In the table-source study, the Memory-only ledger used designer tables while \hesp{} used counted ones. We expected the asymmetry to favour the baseline but did not test this; an LLM may respond non-monotonically to the ledger's scores. The decomposition study uses the counted table for every arm and removes the asymmetry.
  \item[E-8] The v1.0 freezing record stated that no mirrored weights were used. The two Llama-3.1 checkpoints have come from non-gated mirrors since the decomposition study; they are the same files used in every earlier study.
  \item[E-9] (Disclosed deviation.) The v1.0 protocol planned to annotate the Sigma rules on a separate 20\,GB GPU, where phi-4 did not fit. Annotation ran instead on the study's own server with the same model, prompt, schema, and temperature, before anything was frozen; the first machine produced no annotation.
  \item[E-10] \S\ref{sec:realdata} and the ethics section stated that no test split of any public dataset was read. For ExCyTIn-Bench this was false: the two feasibility scripts that measured whether answers can be recovered from the investigation graphs (98.5\%) and whether a fixed catalogue covers them read all 1{,}017 questions of the \texttt{opus5} set, including the 599 test questions. Only the later pivot measurement was restricted to the 418 training questions. No ExCyTIn result evaluates \hesp{} and nothing was tuned on it; the statement holds for GUIDE, whose test split remains unread.
  \item[E-11] (v1.1, disclosed before analysis.) The first v1.1 launch on the H100 server served the model with prefix caching, as on the RTX PRO 6000D. vLLM 0.11 then failed every JSON-mode request of the second study served by a warm server (xgrammar ``Failed to advance FSM''); a controlled rerun reproduced this with caching on and not with caching off. All v1.1 GPU runs on that server therefore use no prefix caching, and the two study directories produced with it were discarded unanalyzed.
\end{description}
